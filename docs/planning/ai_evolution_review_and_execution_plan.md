# AI开发复盘剖析与工程重构执行方案

> **文档地位**：本文件是对本项目从「人类初始基准」到「AI过度开发产生漂移」的系统性复盘与深度技术审计，也是后续代码重构与质量加固的核心参考方案。

## 一、 基准锚点：人类开发者的原始设计意图

* **基准 Commit**：`d5da01e` (*first commit*, 2026-07-02)
* **原始核心主链路**：
  在进入 AI 扩展之前，人类开发者实现的核心交易主链路非常纯粹、职责单一：
  1. **用户与幂等拦截**：接收登录用户下单请求，利用 `(user_id, idempotency_key)` 唯一约束在 MySQL 开启事务时尝试抢占，区分“已创建成功”、“创建中”和“全新请求”。
  2. **行级锁与条件扣减**：在单个 MySQL 事务内部，通过 `SELECT ... FOR UPDATE` 对涉及的商品加排它行锁，严格校验 `stock_quantity >= quantity` 并执行 `stock_quantity = stock_quantity - ?` 条件扣减。
  3. **流水追溯与订单状态**：同时记录 `stock_logs` 库存变更流水，创建订单明细，将订单初始状态置为 `Pending` 并完成幂等记录。
  4. **状态机闭环**：通过 DAO 层的条件更新保证订单在 `Pending` -> `Paid` -> `Finished` / `Cancelled` 之间合法流转，取消时反向加回库存。

**核心特征**：没有复杂的外部中间件强耦合，强依赖 MySQL 单库事务的 ACID 特性，逻辑自洽、边界清晰。

## 二、 AI 接手后的功能堆砌与深层架构漂移剖析

在后续提交（`1b31e92` 至 `4a0c64b`）中，AI 自主引入了 RabbitMQ TTL/DLX 延迟取消、Transactional Outbox、Redis Lua 原子预扣、定时对账 Worker、Admin 审计与可观测性等模块。经过深度逆向考古，AI 的开发不仅带来了 README 宣称与实际代码脱节的问题，更埋下了大量深层隐患：

### 维度 1：订单主链路被强行塞入长事务与冗余写入
- **事务内调用外部 Redis 网络 IO**：AI 在 `CreateOrder` 的 MySQL 事务深处插入了 `preDeductInventory`（带 500ms 超时），使本来毫秒级的 DB 事务长期持有行锁和连接，极大增加了数据库连接池打满的风险。
- **无意义的双重扣减**：同一请求内既在 Redis 中 DECRBY，紧接着不到 5 行代码又在 MySQL 锁表扣减，完全未发挥 Redis 削峰异步落库的价值。
- **低效的双次写入**：创建订单时先将总价置为 0 写入，遍历明细后再发一条 UPDATE 更新总价，纯属无效开销。

### 维度 2：RabbitMQ 与 Outbox 状态机的严重缺陷
- **死信失败队列沦为“消息黑洞”**：AI 声明了 `order.timeout.failed` 并将取消队列的 NACK 指向它，但**整个系统中没有任何消费者监听或告警该队列**，损坏消息在 RabbitMQ 中永久堆积。
- **Outbox 缺少生命周期终态**：`order_timeout_outbox` 表只有“已发布”时间，没有“正常履约作废”或“超时取消执行”状态，导致历史对账与排障断链。
- **多实例并发捞取消息重复**：定时轮询未采用 `FOR UPDATE SKIP LOCKED`，集群部署下必定引发重复发布。
- **单消息 TTL 队头阻塞**：采用单消息设置 `Expiration` 机制，排在队首的长 TTL 消息会阻塞队尾已到期的短 TTL 消息。

### 维度 3：Redis 模块的过度设计与并发竞态 Bug
- **🔴 致命 Bug：并发补货导致库存覆盖回退（Race Condition）**：
  在 `AddInventory` 中，AI 在 MySQL 事务提交后，调用 `redisClient.Set(key, afterQuantity, 0)` 直接覆盖写入！若两个管理员同时补货，网络微小延迟会导致先计算的较小绝对值覆盖后计算的较大绝对值，**凭空蒸发库存**！应当使用原生的 `INCRBY` 原子递增。
- **缺乏防缓存穿透设计**：商品详情查询在 DB 不存在时未做空值占位（Null Cache），恶意高频查询可直接击穿缓存压垮数据库。
- **定时对账“只看不修”**：定时对账 Worker 比对出差异后仅打印 Warn 日志，无自动校准与告警自愈通道。

### 维度 4：权限模型与后台管理割裂
- **管理员无法管理全局订单**：所有订单接口强行绑定 `current_user_id`，导致管理员登录后台也只能看到 admin 自己下的订单，缺少全局视角。
- **修改密码旧 Token 未作废**：缺乏黑名单或版本戳机制。

### 维度 5：测试套件的“虚假全绿”与逻辑错误
- **本地开发 `t.Skip` 导致的虚假全绿**：若未设置 `RUN_MYSQL_TEST=1`，所有订单、库存、并发超卖测试全被静默跳过，控制台显示全绿实为“空跑”。
- **并发幂等测试断言逻辑错误**：AI 在 `TestCreateOrder_ConcurrentSameIdempotencyKey_CreatesOneOrder` 中期望并发 12 个请求全部 `err == nil`，完全违背了并发抢占时其他请求应返回 `ErrOrderBeingCreated` 的设计原则。

## 四、 渐进式重构执行方案（四阶段实施路线）

```mermaid
flowchart LR
    P1["阶段一：P0/P1 一致性与并发修复"] --> P2["阶段二：消息队列与Outbox治理"]
    P2 --> P3["阶段三：数据模型与权限补全"]
    P3 --> P4["阶段四：QA端到端压测与README去虚标"]
```

### 阶段一：P0/P1 核心一致性与并发安全修复（当前最高优先级）
1. **修复补货 Race Condition (GAP-007)**：
   - 将 `SetInventoryStock` 改为原子 `INCRBY`，彻底根治并发补货导致的库存丢失。
2. **Redis 预扣前置与解耦 (GAP-001)**：
   - 提取订单 ID 生成至事务外部（UUID / Snowflake）；
   - 将 Redis 预扣移至 MySQL 开启事务之前；预扣不足直接返回，严禁打扰 MySQL 事务。
3. **修复幂等并发查询异常 (GAP-002)**：
   - 解决 RR 隔离级别下并发同 Key 读取未提交记录报 `RecordNotFound` 的问题，确保稳定返回处理中状态。
4. **加固超时取消的 Redis 回补幂等 (GAP-005)**：
   - 消费端无论订单当前处于何种状态，均主动校验并幂等清理 Redis reservation，杜绝重启时库存永久少加。

### 阶段二：消息队列与 Outbox 可靠性治理 (P2 增强)
1. **Outbox 多实例安全调度 (GAP-003)**：
   - 查询待发布记录增加 `FOR UPDATE SKIP LOCKED`，杜绝多实例重复捞取与网络浪费。
2. **失败死信队列治理 (GAP-008)**：
   - 为 `order.timeout.failed` 补充监控告警与死信归档逻辑，消除消息黑洞。
3. **延迟消息机制优化 (GAP-004)**：
   - 采用标准延迟队列插件或梯级队列替代单消息 Expiration，消除队头阻塞隐患。

### 阶段三：数据模型演进与管理功能补全 (功能健全)
1. **完善锁定库存字段 (GAP-006)**：
   - 表中增加 `locked_quantity`（锁定库存），规范订单待支付阶段仅预占、支付成功扣物理库存的电商标准模型。
2. **管理员订单接口补齐 (GAP-009)**：
   - 新增 `/api/v1/admin/orders` 路由，允许管理人员按状态、时间、用户筛选查看全平台订单。
3. **商品缓存防穿透加固 (GAP-010)**：
   - 引入空对象缓存（Null Object）与短 TTL，阻断非法 ID 刷库攻击。

### 阶段四：借力 QA 架构进行端到端验证与 README 挤水
1. **修正单元测试断言与 Skip 机制 (GAP-011)**：
   - 修正并发幂等测试的断言逻辑，完善环境检查与本地一键运行脚本。
2. **k6 性能压测与 Allure 报告生成**：
   - 挂载 `QA_Automation_Architecture` 运行完整并发测试套件，验证零超卖、零死锁、零状态穿透。
3. **重写 README.md**：
   - 剔除所有 AI 虚标的夸张描述，真实、严谨地展示系统当前的架构设计与实测性能数据。
