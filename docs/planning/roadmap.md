## 一、 当前阶段定位

* **生命周期阶段**：`迭代` / `系统加固`
* **系统纵向层级**：`系统`（边界与通信）· `代码`（事务与锁）· `数据`（模型与一致性）
* **核心目标**：在不破坏现有业务功能与前端演示的前提下，逐项攻坚 `GAP-001` 到 `GAP-006`，使系统的高并发、事务幂等与最终一致性真正达到生产级水准。

---

## 二、 演进路线图（3 阶段迭代计划）

### 阶段一：一致性漏洞与幂等并发修复 (P1 攻坚)
1. **GAP-001 · 预扣前置**：
   - 提取订单号生成至事务外；
   - 将 `preDeductInventory` 移至 `p.db.Transaction` 之前；
   - 编写库存不足时“DB 零命中”的断言测试。
2. **GAP-002 · 幂等并发查询修复**：
   - 优化并发同 Key 冲突处理，避免 RR 隔离级别下的 `RecordNotFound`；
   - 增加高并发同 Key 请求压测与单元用例。
3. **GAP-005 · 超时最终一致性加固**：
   - 优化消费端状态判断：即便订单状态已非 Pending，依然幂等释放/回补 Redis reservation。

### 阶段二：可靠投递与队列拓扑重构 (P2 增强)
1. **GAP-003 · Outbox 多实例无冲突调度**：
   - 引入 `SELECT ... FOR UPDATE SKIP LOCKED` 或轻量级分布式锁机制；
   - 增加指数退避重试。
2. **GAP-004 · RabbitMQ 延迟队头阻塞消除**：
   - 评估采用 `x-delayed-message` 交换机或梯级延时队列方案；
   - 验证交错超时订单的准时触发。

### 阶段三：库存模型规范化与对账自愈 (数据层升级)
1. **GAP-006 · 锁定库存与模型演进**：
   - 编写 Goose 迁移脚本为 `product_inventories` 增加 `locked_quantity`；
   - 显式规范取消链路的加锁排序（`product_id ASC`）；
   - 对账 Worker 引入低峰期核对与告警对接机制。

---

## 三、 质量硬门禁约束

所有改动必须严格遵守项目的本地门禁：
1. **代码与竞态验证**：`go vet ./... && go test -race ./...`
2. **静态代码质量**：`golangci-lint run`
3. **数据库迁移**：`make migrate-validate`
4. **留痕机制**：每次迭代前在 `docs/changes/` 先写变更记录单，通过自验后方可合并提交。
